## 一、时序失序：交付链路的隐性断层

虚拟商品履约链路的脆弱性，从不源于机房断电，而藏于毫秒级的网络时序漂移之中。以《绝地求生》排位赛场景为压力基准：玩家在赛前30秒完成充值支付，此刻移动网络正在4G与5G基站间切换，TCP连接被迫重建；支付网关的异步回调因清算峰值拥塞延迟3~8秒；客户端本地已触发支付成功事件，而服务端事务状态尚未落库——这一"时序漂移窗口"，是绝大多数交付失败的真实根因，与宕机无关。
传统单链路模型将"支付回调→库存扣减→卡密下发"三步串行耦合，任何一跳网络抖动均可导致事务悬挂，用户侧呈现经典的"已扣款未到账"故障态。常规电商场景尚可接受T+1人工核销，但在排位赛开枪前60秒内，这意味着直接的战局损失与不可逆的玩家信任崩塌。

## 二、幂等防线：故障恢复模型的基石

故障恢复模型的第一道防线是严格的幂等性设计。每笔订单在发起时须生成全局唯一幂等键，格式建议为 {uid}_{orderNo}_{skuId}_{timestamp_ms}，写入 Redis Cluster 并绑定TTL。客户端在网络切换或丢包后发起重试，服务端凭幂等键识别重复请求，直接返回原始事务结果，彻底消灭"重复扣款"与"重复下发"两类幂等缺陷，使交易状态可被安全地无限次重查。
幂等层之下，须在客户端构建本地断点续传队列（Local Retry Queue）。支付成功事件触发后，"卡密下发任务"立即写入本地持久化存储（SQLite / LevelDB），任务携带幂等键、重试计数器与指数退避参数。网络中断期间任务静默驻留；网络恢复瞬间（由 NWPathMonitor / ConnectivityManager 原生事件驱动，非定时轮询——后者响应延迟高出前者8~15倍），队列调度器在200ms内激活，按优先级批量上报至服务端补发接口。

## 三、自愈式离线补发引擎：全链路拆解

补发引擎以三层架构运转：
**接入层**：补发接口首查幂等键缓存，命中则直接返回已下发卡密（防重放），未命中则写入消息队列（高可用持久化消息队列 / 高可用持久化消息队列），解耦削峰。
**执行层**：消费者组基于 Saga 模式执行事务补偿——①重查支付网关确认到账；②原子执行库存扣减+卡密分配；③写入下发流水并推送至玩家端。三步任一失败触发局部回滚并重新入队，最终一致性收敛窗口控制在500ms以内。
**监控层**：实时追踪任务存活态，超过3次重试或总耗时超2秒，立即触发自动降级——切换至预热备用卡密池，同步生成人工核销工单。整条链路的端到端 P99 延迟须压制在800ms以内，方能保障玩家在《绝地求生》结算复活窗口（45~90秒）内完成道具到账，实现零感知履约。

## 五、网络容灾交付设计法则

**法则一：幂等优先于重试。** 任何补发逻辑的起点是幂等键校验，裸重试是事故放大器而非修复手段。
**法则二：本地队列是交付的最后生命线。** 服务端任何不可达均不得导致任务丢失，客户端持久化队列必须是架构必选项，而非优化项。
**法则三：Saga 事务边界必须显式界定。** "扣库存"与"下发卡密"须在同一补偿事务内原子完成，严禁跨边界异步分离，否则会在高并发下产生库存扣减成功但卡密未到的幽灵订单。
**法则四：网络感知事件驱动调度。** 补发引擎激活信号必须来自 OS 级网络状态变更，定时轮询的延迟代价在竞技场景下不可接受。
**法则五：备用卡池是 SLA 的硬兜底。** 核心 SKU 须预热隔离备用卡密池，主链路三次失败后自动切换，确保任何网络态下的交付连续性。
